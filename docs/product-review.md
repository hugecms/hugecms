# ECBoot 产品方案评审

> 用途：产品方案评审会汇报材料。基于 [README](../README.md) 产品定义与数据表设计评审结论（2026-10-20）编写。
> 评审目标：确认产品定位、能力方案与实施路线，批准进入开发建模阶段。

---

## 一、评审议题

1. 产品定位与目标市场是否成立；
2. 八大能力域方案是否覆盖 B2C 电商 + 微信私域的完整业务闭环；
3. 实施路线与遗留决策是否可控；
4. **决策请求**：批准冻结数据模型，进入 Models / Factories / Seeders 开发阶段。

## 二、产品定位

### 2.1 一句话定位

**B2C 自营电商 + 微信私域复购增长，双轮驱动**：前台卖货履约，私域沉淀会员，营销撬动复购。

### 2.2 目标用户与解决的问题

| 对象 | 痛点 | ECBoot 方案 |
|---|---|---|
| 品牌商家 / 中小零售企业 | 开源电商（ECShop 等）技术陈旧、无私域能力，SaaS 平台抽佣且数据不在自己手里 | 现代化自营商城，全量数据自持，微信生态原生整合 |
| 消费者 | 多端体验割裂、售后无保障感 | 五端统一账号（UnionID 归一）、售后全流程留痕可追溯 |
| 商家运营 | 活动让利算不清账、触达手段单一 | 优惠逐笔记账可核算、三级触达降级不丢单 |

### 2.3 蓝本与差异化

以 ECShop 2.7.3 数据模型为蓝本逐表重构（88 表全闭环），**去旧补新**：

| 处置 | 内容 |
|---|---|
| 去掉 | 拍卖 / 夺宝 / 团购等过时玩法、贺卡包装、付费调查等陈旧概念 |
| 保留重构 | 商品 / 交易 / 会员 / 物流 / 支付主链路，全部现代化设计（快照、幂等、流水） |
| 补齐新增 | 微信私域 6 表、IM 客服 6 表、秒杀 + 审计、两级分销、多端支付定位、表单引擎、到货提醒、种草图文挂商品 |

> 结论：不是 ECShop 翻新，而是以 ECShop 为骨架校验过的现代电商数据模型。映射明细见 [ECShop 表映射](ecshop-2.7.3-tables-domain-mapping.md)。

## 三、能力方案（八域）

### 3.1 商品 —— 卖点的表达

- 多规格 SKU + 属性体系，支撑服装数码等全品类；
- **五级价格优先级**（秒杀 > 阶梯 > 会员价 > 等级折扣 > 原价）：所有价格玩法共存且有确定规则，运营不纠结；
- 并发安全库存 + 全量流水：大促不超卖，事后可对账；
- 已购验证评价（晒图 / 追评）：口碑资产真实可信。

### 3.2 交易 —— 信任的建立

- 订单全链路快照：任何主数据变更不影响历史订单呈现与售后判定；
- **优惠三源拆分记账**（券 / 积分 / 促销逐笔入 order_promotions）：这是"每场活动真实让利可核算"的数据基础，ROI 报表直接可查；
- 一单多裹 + 物流轨迹 + 部分退款按明细摊销：履约与售后颗粒度到 SKU；
- 售后协商全程留痕、券与积分自动返还：争议可解释，体验有保障。

### 3.3 支付 —— 资金的安全

- 同一渠道按应用配不同商户号：公众号 / 小程序 / APP 各自合规收款；
- 回调幂等三层（渠道去重 → 支付单状态机 → 入账条件更新）：第三方重发不重复入账；
- 资金单据不可物理删除 + 全量回调留痕：对账与审计底气。

### 3.4 会员与账户 —— 资产的归一

- 手机号 + 微信三端授权统一账号，UnionID 跨端归一，粉丝与会员自动关联；
- 积分驱动等级自动升级，等级享折扣与专属价；
- 钱包双资产（余额 / 积分）每笔变动有流水快照；签到持续活跃。

### 3.5 营销增长 —— 复购的引擎

| 玩法 | 关键设计 |
|---|---|
| 优惠券三类（满减/折扣/免邮） | 全生命周期状态 + 核销订单关联，退款自动返还 |
| 满减/折扣促销 | 按全场/分类/品牌/商品圈范围 |
| 秒杀 | 原子库存 + 审计流水 + 超时回补，防超卖可对账 |
| 两级分销 | 带参二维码扫码即绑定，计佣绑定快照防漏算，退款佣金失效 |
| 专题页 | 运营自定义聚合落地页，定时上下线 |
| 种草内容 | 图文挂商品，评论/点赞/关注社区化互动 |

### 3.6 微信私域 —— 差异化壁垒

- 粉丝资产独立管理（标签/来源/取关留痕），矩阵多号共存，换绑不串数据；
- 触达双通道（公众号模板 + 小程序订阅消息授权账本）；
- 带参渠道码三类，扫码 / 注册转化双计数——**渠道 ROI 有了归因闭环**；
- **三级触达降级**（微信 → 站内信 → 短信）+ 统一触达视图：重要消息永不丢。

### 3.7 客服 —— 转化的兜底

- IM 实时会话 + 机器人关键词分流 + 转人工兜底；
- 空闲优先智能分配、话术库、满意度评分；
- 咨询带商品 / 订单 / 微信上下文，售前转化与售后承接同一条链路。

### 3.8 平台运营 —— 效率的杠杆

广告位与投放排期、搜索热词、每日经营统计（明细与汇总分层，口径可重算）、操作日志、IP 黑名单、敏感词——运营位后台全可配，风控审计完备。

## 四、业务闭环（核心逻辑）

```
带参二维码 / 广告位 / 种草图文          ← 获客（归因可查）
        ↓
微信授权 / 手机号注册 → 统一会员        ← 资产归一（UnionID）
        ↓
浏览 · 足迹 · 收藏 · 搜索 · 到货提醒     ← 转化铺垫
        ↓
购物车 → 下单（优惠拆分记账）→ 支付     ← 交易（幂等可对账）
        ↓
发货（一单多裹·轨迹）→ 收货 → 评价      ← 履约（全流程留痕）
        ├ 售后按明细摊销返还 + 客服承接
        ↓
分销计佣 / 等级成长 / 三级触达召回       ← 增长引擎
        ↓
复购 ↺
```

**每个环节均有数据表支撑**，2026-10-20 全链路走查结论：无阻断性缺口。

## 五、技术可行性概览（支撑性结论）

| 项 | 现状 |
|---|---|
| 数据模型 | 13 域 / 91 表 + 1 视图，`migrate:fresh` 全通过；ECShop 88 表蓝本映射全闭环 |
| 设计规范 | 命名 / 时间字段 / 软删 / 索引全库统一，无外键（应用层状态机条件更新） |
| 核心机制 | 库存防超卖、支付幂等三层、优惠拆分返还、资金流水、触达降级、客服分流——六大机制评审通过 |
| 技术栈 | PHP 8.4 + Laravel、MySQL、GatewayWorker、easywechat——全部成熟组件 |

技术细节不作为本次评审重点，详见 [数据表设计技术文档](database-design.md)。

## 七、风险与待决事项

| # | 事项 | 影响 | 处置建议 |
|---|---|---|---|
| 1 | 粉丝↔会员自动归一依赖 UnionID | 未绑开放平台则私域矩阵失效 | **上线前必须确认**已绑开放平台 |
| 2 | 统计 pv/uv 数据源未定 | 经营统计缺输入 | 接第三方统计 API 落数，统计功能上线前拍板 |
| 3 | 余额抵扣表达、秒杀叠加规则、超时窗口 | 应用层规则空位 | 开发期落 system_settings，见 [遗留决策点](pending-decisions.md) |
| 4 | 虚拟商品业务 | 发码/免物流流程缺失 | 维持业务信号触发，不提前建设 |

以上均**不阻塞阶段①启动**。
