## 二、总体策略

1. **双工作流并行**：
   - **W1 功能开发流**：按「交易主链路 → 营销增长 → 微信私域 → 客服」顺序纵向切片交付，每个里程碑产出可演示版本；
   - **W2 数据迁移流**：M2 期间启动方案设计与脚本开发，与功能开发并行试迁演练，最终在 M6 割接对齐。
2. **机制先行**：六大核心机制在所属里程碑内作为首要任务（P0），先于外围功能——它们是正确性地基，返工代价最高。
3. **无外键纪律**：全库一致性依赖应用层条件更新与流水追溯，所有状态流转代码必须走「状态机条件更新」模式并配套测试，纳入代码评审一票否决项。
4. **决策点前置拍板**：遗留决策点绑定里程碑拍板时限（第九节），避免开发中途回改。

## 五、数据迁移专项计划（W2）

### 5.1 范围与映射

- **来源**：ECShop 2.7.3 生产库（`ecs_` 前缀 88 表）；
- **需迁移**：约 65~70 张业务表（映射矩阵以 [表映射文档](ecshop-2.7.3-tables-domain-mapping.md) 为准）；
- **不迁移**：sessions/sessions_data/error_log/stats/searchengine/adsense/admin_message/user_feed 等运行时与低价值表；
- **已废弃概念**（贺卡/包装/拍卖/夺宝等）不迁；`ecs_comment` 按 subject_type 拆分迁移。

### 5.2 迁移批次（顺序即依赖）

| 批次 | 内容 | 依赖 |
|---|---|---|
| B1 基础数据 | ecs_region→system_regions、ecs_shop_config→system_settings、字典 | — |
| B2 组织与权限 | ecs_admin_user/role/admin_action→admin_* | B1 |
| B3 用户与会员 | ecs_users（含 rank/balance/points）→users+user_profiles、地址、收藏、account_log 流水 | B1 |
| B4 商品 | ecs_goods/category/brand/type/attribute/products/member_price/volume_price/gallery→product_*/system_attachments | B1 |
| B5 交易历史 | ecs_order_info/goods/action/delivery/back→orders/order_items/order_logs/order_shipments/order_refunds（含状态机映射、金额对齐） | B3, B4 |
| B6 营销与内容 | ecs_bonus(类型+用户红包)、favourable_activity、article/comment→marketing_*/content_* | B3, B4 |

### 5.3 脚本工程

- 形态：Laravel Console Commands，按批次分命令，`--dry-run / --execute / --verify` 三段式；
- **幂等可重跑**：以业务唯一键 upsert，不以自增 ID 判断；
- ID 策略：新旧 ID 映射表（或统一以业务唯一键关联，与全库「跨域用业务键」约定一致）；
- 清洗规则：密码不可逆→统一重置强制登录改密；敏感配置加密落库；时间字段时区对齐；金额精度对齐 decimal(10,2)；历史订单快照字段（收货人/商品名/价格）从原表冗余字段回填。

### 5.4 对账体系（三层）

1. **计数对账**：每表 `源 count = 目标 count`（含软删口径说明）；
2. **金额对账**：订单总额、用户余额合计、积分总量、红包面值合计——源/总/目标三方一致；
3. **抽样比对**：每批次随机抽 N 条逐字段比对（N≥50），差异清单归零。

### 5.5 演练与割接

| 阶段 | 内容 | 时点 |
|---|---|---|
| 试迁 | 小样本（10%）跑通全批次 | W8–W9 |
| 全量演练 | ≥2 轮全量 dry-run+execute，记录耗时作为割接窗口依据 | W12、W14 |
| 割接 Runbook | 停写→备份→执行→对账→切流量→放开，含每步回滚点 | W15 定稿评审 |
| 割接执行 | 按窗口执行，原库保留只读 ≥30 天 | W16 |

### 5.6 迁移关键决策（需在 W6 前拍板）

| 决策 | 建议 |
|---|---|
| 历史订单迁移范围 | 全量迁移（售后追溯与财务对账需要） |
| 同手机号多账号合并策略 | 以最近登录为主账号，合并前出冲突清单人工确认 |
| 旧密码处理 | 不可逆，统一重置 + 首登短信验证改密 |

## 六、测试与质量保障

- **分层**：单元（价格计算、分摊、状态机）→ 功能（API 全链路、六大机制场景）→ 契约（支付回调报文）→ 压测（秒杀并发、支付回调重放）；
- **六大机制必测清单**：并发防超卖（locked_stock/sold_stock 条件更新）、支付回调重发幂等、优惠三源拆分与退款返还、余额/积分流水 from/to 快照、触达三级降级、客服分配流转；
- **门禁**：CI 三件套（Pint/PHPStan/PHPUnit）全绿方可合并；状态流转未走条件更新的 PR 一票否决；
- **测试数据**：一律走 Factories（M1 交付物），禁止手工造数。
